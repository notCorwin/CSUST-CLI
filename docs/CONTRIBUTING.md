# 贡献与验收

贡献的最小单位不是“再加一个网页入口”，而是一项有明确用户价值、业务边界和结果证据的能力。下面的流程用于新增服务、扩展既有业务和更新项目文档。

## 先决定改哪里

| 变化 | 首选位置 | 判断标准 |
| --- | --- | --- |
| 某服务的字段、路径或状态变化 | 对应 adapter | 不让协议细节扩散到其他服务 |
| 两个以上服务共享的请求/会话行为 | 共享 transport | 先确认确实是共同语义，不为一个服务抽象 |
| 跨服务的 `ok`、确认或置信度规则 | `internal/contract` | 规则必须能适用于所有调用者 |
| 服务入口、证据和可用性变化 | 服务目录及相关测试 | 记录证据，不把推测写成能力 |
| 稳定的业务解释或使用边界 | `docs/` | 不复制完整命令帮助和端点清单 |

## 新增业务能力清单

开始编码前，先回答：

- 谁会使用它：学生、教师、管理员还是公开访客？
- 它属于查询、提交、审核、撤回、删除、下载还是认证？
- 需要哪个服务、账号、角色、VPN 或二次认证？
- 目标对象如何从查询结果唯一确定？
- 远端明确成功、明确拒绝和结果未知分别长什么样？
- 是否需要写后回读、状态探针或文件落盘验证？
- 哪些服务特有字段必须保留，哪些字段才有资格进入统一模型？

如果这些问题无法回答，应先做有限探索，不要先添加一个看起来通用的请求入口。

## 参数与结果设计

公共命令使用业务语言：学期、课程、日期、角色、申请、资源、消息和文件。内部路径、隐藏字段、接口动作名、服务端分页键和前端组件名称不应成为公共参数。

统一结果只承诺跨服务稳定的状态语义；业务数据按服务保留原始字段和特有能力。对不确定值使用明确的未知/未验证表示，不用空值掩盖解析失败。

所有可能改变远端状态的业务操作都要：

1. 要求显式确认；
2. 记录是否已提交；
3. 识别服务拒绝；
4. 尽可能执行回读或状态验证；
5. 在证据不足时返回 `mutation_unverified`，而不是乐观成功。

## 测试最低要求

测试使用本地 `httptest` 或等价的模拟服务，不依赖真实账号、学校网络、当前学期或上游在线状态。根据改动范围至少覆盖：

- 业务字段映射和语义参数；
- 登录成功、未登录、权限不足和验证码/二次认证分支；
- 写操作的确认开关；
- 明确成功、明确拒绝和结果未知；
- 写后回读或文件保存；
- 会话隔离、路径校验和敏感值脱敏；
- 未来增加字段时的兼容性。

不需要为每个简单分支建立重复 fixture；但每项非平凡的业务逻辑至少应有一个能在逻辑失效时失败的检查。

## 文档更新规则

需要更新文档的情况：

- 用户必须知道的网络、账号、角色、时间窗口或人工步骤变化；
- `ok`、`confirmed`、`pending`、`evidence` 或错误处理语义变化；
- 服务发现证据、能力等级或已知限制变化；
- 新增一类业务对象或公共参数语义。

不需要手工抄写到文档的内容：

- 完整命令列表和参数列表；
- 每个 endpoint、隐藏表单字段或前端 bundle 细节；
- 只对当前提交成立的局部实现结构；
- 没有探测证据的服务推测。

README 用于入门，专题文档用于稳定语义，`--help` 用于命令语法，`services catalog` 用于当前服务证据。

## 本地验收

提交前运行：

```bash
go test ./...
go vet ./...
go build ./...
go run . --help
git diff --check
```

如果改动涉及认证、文件、写操作或目录证据，还要说明对应的模拟场景和成功判定。线上服务无法访问时，报告“未验证”并保留原因，不把本地单元测试写成线上验收。

## 问题报告和评审信息

问题报告应包含：服务名称、业务意图、脱敏后的命令、网络/认证前提、返回的 `code`、`evidence`、`submitted`/`confirmed` 状态，以及是否可以安全重试。

评审重点是：业务边界是否清楚、是否重复了已有 helper、是否把网页细节暴露给调用者、写操作是否有证据、失败是否会导致重复提交，以及文档是否写了代码无法表达的规则。
