# CSUST CLI 结果契约

本文说明智能体和脚本如何解释 `--json` 输出。它描述的是跨服务稳定的状态语义，不是某个上游接口的完整响应 schema；业务字段仍由具体服务决定。

## 输出边界

- 机器调用使用 `--json`，从标准输出读取一个 JSON 对象。
- 进程退出码表示 CLI 调用是否遇到错误；它不能单独证明远端写入成功。
- 业务数据、原始响应和错误详情可能同时存在，但敏感字段应已经脱敏。
- 未知命令、参数错误、认证失败、网络失败、业务拒绝和未确认写入都应被调用者区别处理。

## 公共状态字段

| 字段 | 语义 | 不应作出的推断 |
| --- | --- | --- |
| `ok` | 当前 CLI 流程的总体状态 | 不能单独证明写入已完成 |
| `code` | 机器可分支的结果类别 | 不能当作上游 HTTP 状态码使用 |
| `error` | 面向调用者的可读说明 | 不能稳定依赖完整文案 |
| `submitted` | 是否发出可能改变远端状态的请求 | 不代表服务端接受或持久化 |
| `confirmed` | 是否取得足够的成功证据 | 只对当前返回的证据负责 |
| `evidence` | 成功、拒绝或未确认的判定依据 | 不是通用枚举的完整封闭集合 |
| `pending` | 流程仍在等待后续步骤 | 不代表最终失败或成功 |
| `next` | 建议的后续步骤或续办阶段 | 不代表该步骤已经执行 |
| `details` | 业务上下文、回读原因或续办信息 | 其中的服务特有字段不能跨服务套用 |

成功的只读结果通常是 `submitted=false, confirmed=true`；成功的写结果至少应是 `submitted=true, confirmed=true`。如果请求可能改变远端状态却没有确认依据，结果必须保留未确认状态。

## 调用者决策表

| 状态组合 | 解释 | 推荐动作 |
| --- | --- | --- |
| `ok=true, submitted=false` | 查询或状态探针完成 | 消费业务数据 |
| `ok=true, submitted=true, confirmed=true` | 写入有服务信号或回读证据 | 记录完成，不重复提交 |
| `ok=true, pending=true` | 当前步骤完成，但整个流程未结束 | 按 `next` 继续 |
| `ok=false, submitted=false` | 写请求尚未发出 | 修正参数、认证或网络后重试 |
| `ok=false, submitted=true, code=mutation_rejected` | 服务明确拒绝写入 | 读取原因，修正条件后再提交 |
| `ok=false, submitted=true, code=mutation_unverified` | 请求可能已到达，结果未知 | 先只读回查，不要自动重试 |

错误结果仍应优先读取 `submitted`、`confirmed` 和 `evidence`，因为失败发生在写请求之前和之后，处理方式不同。

## 主要错误类别

错误码会随着服务能力增加，但通常可以按下面的业务类别处理：

| 类别 | 典型代码 | 处理方式 |
| --- | --- | --- |
| 调用不完整 | `invalid_argument`, `confirmation_required` | 不访问或不提交远端，修正调用 |
| 凭据/认证 | `credentials_required`, `login_required`, `captcha_required`, `tfa_required` | 补充凭据、验证码或续办步骤 |
| 权限/业务条件 | `permission_denied`, `business_rejected`, `not_found` | 不盲目重试，检查角色、资格、时间窗口和对象 |
| 上游/协议 | `service_unavailable`, `response_error`, `parse_error`, `protocol_error` | 保留证据，先判断服务变化还是网络问题 |
| 写入结果 | `mutation_rejected`, `mutation_unverified` | 分别按明确拒绝和结果未知处理 |
| 本地状态 | `cookie_write_failed`, `session_error`, `output_write_failed`, `state_*` | 检查本地会话、状态文件或输出路径 |

不要依赖错误文案做程序分支；文案服务于人，`code` 和状态字段服务于机器。

## 待续流程

验证码、短信、邮件、密保、TFA 和密码找回可能需要多次调用。待续结果应包含足够的阶段信息或状态文件路径，调用者应：

1. 保存续办所需的非敏感标识和 `next`。
2. 由人工或外部系统取得验证码/确认码。
3. 使用同一服务和正确的会话继续调用。
4. 在最终返回前不要把“验证码已发送”解释成“登录成功”或“密码已修改”。

如果续办状态丢失，优先重新执行只读的初始步骤；不要拿旧服务的状态文件或旧验证码跨服务使用。

## `confidence` 与证据

目录或页面/响应对象中的 `confidence` 描述发现或解析证据的强弱，不描述当前用户权限，也不描述业务成功概率。`low` 置信度结果必须同时有具体的 `confidence_evidence`，否则不能作为可靠结论。

可以这样使用它：

- `high`：有可重复的结构化协议、登录探针或明确业务响应，可进入正常调用流程。
- `medium`：有公开页面、前端资源或部分协议证据，适合只读验证，不应自动扩大能力承诺。
- `low`：入口不可达、默认页、拒绝访问或证据不足，只能记录状态并等待重新发现。

这三个级别是维护决策信号，不是学校服务的官方等级。

## 文件响应

需要保存 PDF、图片、表格或其他二进制内容时使用 `--output`。调用者应检查返回结果和目标文件是否存在；不要把“远端返回下载链接”当成本地文件已经成功保存。写入失败不应覆盖已有的完整目标文件。

## 兼容性原则

调用者应只依赖公共状态字段和自己请求的业务字段，忽略未来增加的字段；不要依赖字段顺序、完整错误文案、内部 URL 或服务端隐藏字段。文档中的示例 JSON 是语义示例，不是所有命令的完整响应。
