# CSUST CLI 使用与业务边界

本文说明使用者和智能体在调用 CSUST CLI 时需要知道的前提、判断方式和维护约定。它不列出服务端地址、表单字段或完整命令表：这些内容属于易变的适配实现，应以当前版本的 `--help` 和 `services catalog` 为准。

## 这是什么

CSUST CLI 把分散在统一认证、VPN、教务、服务大厅和多个独立系统中的业务，整理成可组合的命令。它面向的是“查什么、申请什么、修改什么”这样的业务意图，而不是某个网页上的按钮或接口路径。

学校网站是外部依赖，且不同系统的认证方式、权限模型和协议稳定性不同。因此，CLI 的覆盖范围按**可验证的业务能力**计算，不按页面数量或站点数量计算：一个只有登录入口的系统，可靠支持可能只有状态、登录和退出；一个有稳定查询协议的系统，才继续抽象具体业务。

CLI 不是无头浏览器，也不是通用爬虫。浏览器只用于开发阶段发现能力；运行时不会启动浏览器，也不会把网页 DOM 当成公共接口。需要浏览器执行 JavaScript、设备认证或人工交互的场景，应回到原服务完成。

## 三个容易混淆的概念

| 概念 | 应如何理解 |
| --- | --- |
| 服务 | 一个学校业务系统或入口。服务可能需要独立账号、独立会话或 VPN 前置条件。 |
| 命令 | 面向业务对象的稳定调用方式，例如按学期查询课程或按日期查询预约；不应要求调用者知道网页字段。 |
| 目录 | 在某次探测中发现的入口及其证据。目录既可以记录已映射能力，也可以诚实记录当前不可达、默认页或拒绝访问的入口。 |

目录中的条目不等于当前账号一定有权限，也不等于该服务提供长期稳定的 API。调用前应以当前命令的返回结果为准。

## 一次调用的推荐流程

对于智能体或脚本，建议把一次业务拆成下面的状态流：

```text
业务意图
  → 查看目录/帮助
  → 确认网络、身份和会话
  → 只读查询或状态探针
  → 从返回结果选择业务对象
  → 明确确认后执行写操作
  → 根据结果证据决定完成、续办或回读
```

1. 先把任务翻译成业务对象：课程、成绩、预约、申请、消息、文件或账号设置。
2. 使用 `services catalog` 和命令帮助确认当前版本是否有对应能力；不要根据相似网页名称猜测命令。
3. 先执行只读查询或 `status`，确认当前网络、登录状态、角色和权限。校内网、VPN、服务账号和业务开放时间都是外部前置条件。
4. 写操作的目标应来自本次查询返回的标识和状态，不要凭页面顺序或旧记录臆造 ID。
5. 写操作必须显式表达确认意图。结果返回后，不只看进程退出码或一句“请求已发送”，还要判断 `submitted`、`confirmed` 和 `evidence`。

## 认证、验证码与会话

不同系统的 Cookie、Token、角色和失效条件不一定相容。教务、VPN、图书馆、网络教学和独立业务服务的会话不能因为“都是同一个学校账号”就相互替代；VPN 会话还可能只是其他内网业务的传输前置条件。

登录流程可能分多步完成：

- 图形验证码由调用者或外部人工流程提供；CLI 不把猜测的 OCR 结果当作认证成功。
- 短信、邮件、密保、二次认证或 TFA 会返回待续状态。`pending`/`next` 表示下一步，而不是最终登录或业务完成。
- 密码、验证码、Token 和会话文件都属于敏感信息。优先使用标准输入或环境变量，不要把秘密写入命令历史、Issue、日志或 JSON 任务记录。

如果登录成功但后续查询仍返回登录页，应把它视为会话失效、角色不匹配或网关问题排查，不要把登录页解析成“没有数据”。

## 如何判断结果

机器调用应优先使用 `--json`。公共结果字段表达的是状态，而不是对某个服务内部响应字段的承诺：

| 结果 | 含义 | 下一步 |
| --- | --- | --- |
| `submitted=false` | 没有发出可能改变远端状态的写请求 | 可修正参数、认证或网络后重试 |
| `submitted=true, confirmed=true` | 写请求已发出，并取得服务成功信号或回读证据 | 业务可视为已确认完成 |
| `submitted=true, confirmed=false` 且为 `mutation_rejected` | 服务明确拒绝写入 | 修正业务条件后再提交 |
| `submitted=true, confirmed=false` 且为 `mutation_unverified` | 请求可能已到达，但结果证据不足 | 先查询远端状态，不要盲目重试 |
| `pending=true` 或存在 `next` | 流程仍等待验证码、短信、邮件或其他步骤 | 按 `next` 续办，不能当成最终成功 |

`ok` 是本次 CLI 流程的整体结果；它不能替代对写操作的 `confirmed` 判断。进程退出码只用于判断 CLI 是否遇到错误，不能单独证明远端业务已经写入。

`evidence` 说明判定依据。目录或响应中的 `confidence` 是对发现/解析证据的描述，不是当前用户权限或业务成功率；`low` 置信度内容必须结合 `confidence_evidence` 谨慎使用。

## 失败时不要先重试

看到失败时，先区分四类问题：

1. **入口或网络问题**：连接失败、网关错误、服务不可达；先确认网络环境和服务状态。
2. **认证或权限问题**：未登录、登录页、验证码失败、角色不允许；先恢复正确会话。
3. **业务拒绝**：参数、资格、时间窗口或重复提交不满足条件；读取返回的业务原因。
4. **结果未知**：写请求已发出但没有足够回读证据；先查询状态，再决定是否需要人工确认。

尤其不要对密码修改、报名、预约、缴费、删除、撤回、审批和文件提交等操作自动重试。未知结果下的第二次提交可能造成重复业务。

## 维护者应保护的约定

- 公共参数描述业务概念；协议字段、隐藏令牌、页面动作和内部路径留在对应 adapter 内。
- 能通过结构化协议完成的能力不退回 DOM 自动化；确实只能解析旧页面时，也把解析限制在该服务边界内。
- 先定义成功、拒绝和未知结果的证据，再实现写请求；成功响应但没有回读时，应明确返回未确认。
- 新能力优先复用现有请求、会话、分页、验证码、文件和结果处理逻辑，不为单个服务复制一套 transport。
- 用本地 HTTP 测试服务覆盖字段映射、认证状态、成功/拒绝/未知结果和敏感值脱敏；测试不依赖真实账号或学校在线状态。
- 发现新服务或服务变化时，更新目录中的证据和日期；文档只记录仍然有效的业务规则，不把一次探测结果写成长期承诺。

## 何时应回到网页

以下情况不应强行包装成 CLI 能力：需要浏览器指纹或设备认证、必须执行复杂页面脚本、只能通过可视化拖拽完成、需要人工确认原始材料，或服务没有足够证据证明对应协议仍可用。CLI 应返回明确的不可用/待人工状态，而不是伪造一个看似成功的结果。

问题反馈请附上脱敏后的命令、服务名、网络/登录前提、JSON 中的 `code` 与 `evidence`，以及是否已经出现 `submitted=true`；不要附带密码、Token、Cookie、验证码原图或会话文件。
