# CSUST CLI 设计与维护说明

本文记录项目中不适合只靠代码阅读推断的上下文：项目为什么采用直接协议适配、各层负责什么、写操作如何判定成功，以及服务变化时应在哪里维护。安装和命令用法以 [README.md](../README.md) 为准；专题文档入口见 [docs/README.md](README.md)，调用者和智能体的认证、续办及结果处理见 [OPERATING_MODEL.md](OPERATING_MODEL.md)。本文不复制服务端接口清单，因为接口、页面和可用性会变化。

## 1. 项目意图

CSUST 的业务入口分散在统一认证、VPN、服务大厅、旧式 HTML 表单、CAS、JSON 服务和若干独立系统中。项目的目标不是把这些页面搬进终端，而是把对学生、教师和智能体有意义的业务对象统一成可组合的 CLI 命令。

这里的“覆盖”按业务能力衡量，而不是按页面或 URL 数量衡量。一个页面只有登录框时，能可靠表达的能力可能只有状态、登录和退出；一个页面背后有公开查询或提交协议时，才继续抽象对应业务。当前不可达、只有默认页或只有拒绝访问响应的入口，也只能记录其可验证状态，不能为了看起来完整而猜测业务接口。

网站探索按以下优先级决定投入深度：

| 类别 | 含义 | 维护策略 |
| --- | --- | --- |
| `CORE` | 教务、认证、学生高频事务 | 深入发现协议，优先保持稳定语义和成功回读 |
| `ENABLER` | 认证、权限、VPN、网关和会话 | 深入维护，因为多个业务依赖它们 |
| `UNIQUE` | 学校特有的档案、实验、评价等业务 | 深入抽象，保留服务特有字段 |
| `COMMODITY` | 可由通用产品替代的能力 | 只实现有明确业务价值的部分 |
| `CONTENT` | 纯展示或静态内容 | 只提供必要的读取入口 |
| `UNKNOWN` | 证据不足以分类 | 继续有限探索，直到能归类或确认不可达 |

## 2. 核心边界

### 运行时不是浏览器

Playwright 只用于开发阶段观察页面、网络请求和返回内容。正式命令不启动浏览器、不执行页面 JavaScript，也不依赖浏览器 DOM。能由接口、协议或结构化响应完成的能力，必须直接调用；只有没有独立协议的旧页面，才在对应 adapter 内解析 HTML 作为兼容层。

这条边界带来两个维护结论：

- 页面改版不应直接导致整个 CLI 改成浏览器自动化；先确认业务协议是否仍然存在。
- 如果确实只能靠页面表单完成，页面解析代码应留在具体 adapter 中，不能扩散到命令层或共享 transport。

### 语义层与协议层分离

用户看到的是业务概念，例如学期、课程编号、预约日期、档案对象和收件信息；网页字段名、表单动作、隐藏令牌、分页参数和内部路径只属于 adapter。这样做的原因是同一业务概念可能在不同系统中有不同字段，而网页实现细节不应成为公共 CLI 接口。

适配器同时保留服务特有的原始数据、字段集合或页面证据。统一模型负责让智能体能稳定组合查询；原始部分负责避免抽象过程丢失该服务仍然有用的能力。

### 页面可用性与业务可用性分开

HTTP 200 只说明拿到了响应，不说明用户已登录、业务存在或写操作成功。目录中的能力依据包含服务状态、页面类型、结构化响应、登录探针和写后回读等不同证据。维护时必须区分：

1. 入口可访问；
2. 页面或接口可解析；
3. 当前会话有权限；
4. 远端接受了写请求；
5. 写入结果已经被回读或其他业务信号确认。

## 3. 请求流和代码分层

```text
命令行参数
    │
    ▼
main.go：版本、JSON 模式、进程退出码
    │
    ▼
NativeSite.Run：按领域分发命令
    ├─ 教务与学生核心 adapter
    ├─ VPN adapter
    ├─ VPN 网关 adapter（网络教学、教学质量）
    └─ 独立业务 adapter（档案、图书馆、招生、期刊等）
    │
    ▼
internal/adapter/site.go：HTTP、Cookie、重定向、文件和脱敏
    │
    ▼
学校服务协议
    │
    ▼
contract.Normalize / NormalizeError：统一 JSON 结果
```

各层的职责如下：

| 位置 | 应负责 | 不应负责 |
| --- | --- | --- |
| `main.go` | 处理进程级参数、版本、标准输出和退出码 | 认识某个学校页面的字段或接口 |
| `internal/contract` | 约束成功、失败、待续流程和置信度的公共结果 | 发起网络请求或理解业务页面 |
| 领域 adapter | 语义参数、协议映射、业务解析和成功判定 | 重复实现 Cookie、重定向和文件写入 |
| `site.go` | 共享 HTTP transport、会话文件、限制、脱敏、二进制保存 | 决定某个业务字段是否有效 |
| `gateway.go` | 通过 VPN 会话发现网关服务并拼接受控路径 | 接受任意外部主机或把网关变成通用爬虫 |
| 测试 | 用本地 HTTP 服务验证映射和状态转换 | 使用真实账户或依赖当前学校网络 |

`NativeSite.Run` 的分发顺序是有意保留的：核心登录、教材、教务、VPN、网关和独立业务命令共享别名时，必须先由更具体的领域处理，避免一个新业务命令意外改变既有命令的含义。新增命令前应先检查既有分发器和别名。

## 4. 四类适配路径

### 教务核心

教务 adapter 面向高频学生事务，通常需要登录会话、服务端表单和旧式页面解析。它负责把课程、成绩、考试、选课、申请和消息等业务转成稳定参数，并在有写操作时执行回读。不要把教务内部字段直接暴露给命令调用者。

### VPN 与认证

VPN 既是一个用户业务，也是多个内网服务的传输前置条件。它有独立的 Cookie、会话状态和可能的二次认证流程。二次认证、短信或邮件验证属于可续流程，不能在一次命令中假装已经完成。

### 网关业务

网络教学和教学质量服务的实际地址由 VPN 当前会话提供，不能假设固定后端主机。网关 adapter 先发现当前服务前缀，再在该服务命名空间内请求；路径必须经过校验，不能接受绝对 URL、目录跳转或越过当前服务的主机。

### 独立业务服务

独立系统统一使用服务名、站点配置和业务 catalog，但每个服务仍由自己的 adapter 负责协议差异。适合复用的部分是请求 transport、凭据读取、验证码保存、分页和结果包装；业务字段、状态码和成功证据应留在服务边界内。

## 5. 会话与凭据的设计

不同学校系统的 Cookie、Token、登录角色和失效条件并不相同。项目按服务入口的主机和端口划分默认会话文件，默认不把一个主机的 Cookie 带给另一个主机；同一主机上的入口可能共享文件，这是协议或显式会话路径造成的边界，而不是按命令名隔离。需要额外访问令牌的服务把令牌作为独立会话状态管理，而不是混入公共命令参数。

凭据来源按“显式优先、避免进入命令历史”的原则处理：可使用标准输入或对应环境变量，部分场景兼容 `.env`。密码、Token、会话和隐藏字段不会作为普通结果回显；请求、错误和页面快照中的敏感值也必须经过脱敏，验证码值也不应主动写入输出。文档示例只能使用占位符。

验证码不自动依赖 OCR。adapter 在拿不到验证码值时保存图片并返回 `captcha_required`，调用者查看图片后再次提供 `--captcha`。这保留了所有需要人工确认的认证流程，也避免把不可验证的识别结果当成成功登录。

## 6. 结果契约与写操作

机器调用主要依赖以下字段：

```json
{
  "ok": true,
  "submitted": true,
  "confirmed": true,
  "evidence": "server-success-and-readback"
}
```

- `submitted` 表示是否已经发出可能改变远端状态的请求，不表示请求一定成功。
- `confirmed` 表示 adapter 已取得足够的业务证据，例如明确成功状态、成功响应、登录探针或写后回读。
- `evidence` 说明判定来源，供智能体决定是否继续、重试或请求人工介入。
- `pending` 与 `next` 表示流程尚未结束，例如等待短信、邮箱或第二认证码；此时不能把 `ok` 当成最终业务成功。

业务数据、凭据和账户设置等写操作都需要显式 `--yes`；认证登录、退出和获取验证码等会话动作由具体 adapter 明确分类。共享 transport 会按 HTTP 方法和已知副作用路径做基础判断，领域 adapter 还要处理服务特有的写入语义。成功判定的优先级通常是：结构化成功状态最高，其次是明确业务文本或写后回读；只有“请求已发出”而没有结果证据时，必须返回未确认，而不是乐观成功。

失败要区分“远端明确拒绝”和“结果未知”：

- `mutation_rejected`：服务明确表示没有写入，可以修正参数后重试。
- `mutation_unverified`：请求可能已到达，但响应、会话保存或回读不足以判断结果；应先查询远端状态，不要自动重试。

文件下载使用临时文件和原子替换，已有目标不会被半截响应覆盖。响应体、请求体和文件大小有明确上限，防止异常服务把一次 CLI 调用变成无界内存或磁盘操作。

## 7. 重要决策及原因

| 决策 | 原因与代价 |
| --- | --- |
| 运行时直接调用 HTTP/CAS/JSON/表单协议 | 依赖少、启动快、结果可测试；代价是服务协议变化需要维护 adapter |
| 用 adapter 隔离网页实现 | CLI 语义稳定，页面变化的影响集中；代价是每个新系统要建立字段映射 |
| 统一结果字段，同时保留原始数据 | 方便智能体组合，也不牺牲服务特有能力；代价是结果可能同时有语义和原始两层 |
| 每个服务隔离会话 | 避免错误身份和 Cookie 泄漏，支持不同账号；代价是登录次数和会话文件更多 |
| 写操作显式确认并要求证据 | 防止把未确认状态误报给调用方；代价是部分流程需要额外回读或人工续办 |
| 动态发现 VPN 网关 | 适应当前账号和环境的服务分配；代价是状态命令需要先访问 VPN |
| 验证码由调用者提供 | 不隐藏 OCR 依赖，不把猜测当认证结果；代价是自动化流程需要人工或外部识别步骤 |
| 不可达入口只记录状态 | 保持证据诚实；代价是目录不能承诺尚未验证的业务 |

## 8. 新增或修改 adapter 的流程

1. 先确认业务价值、账号角色、读写边界和成功证据；不要从页面数量推断工作范围。
2. 在开发环境用 Playwright CLI 观察真实页面、请求、响应和状态变化。Playwright 脚本和浏览器控制不进入 Go 运行时。
3. 检查是否已有 `siteRequest`、Cookie、验证码、分页、HTML 解析、JSON 状态或回读 helper；优先复用，不新增一套 transport。
4. 选择合适的领域边界。已有业务服务通常只需补服务配置、命令分支、语义参数和 adapter；只有跨领域协议才修改共享层。
5. 把网页字段翻译成语义参数，并为服务特有字段保留原始值。不要把内部 URL、隐藏字段名变成公共 CLI 参数。
6. 先写成功判定，再实现写请求：明确服务成功状态、拒绝状态、登录失效表现和回读条件。
7. 用 `httptest` 添加最小测试，至少覆盖字段映射、成功/拒绝/未知结果、确认开关、会话或 Token 保存，以及敏感值不泄漏。
8. 同步更新命令帮助、README 的用户用法和服务目录证据；文档写设计原因，不复制易变的端点清单。
9. 运行完整检查：

   ```bash
   go test ./...
   go vet ./...
   go build ./...
   go run . --help
   git diff --check
   ```

## 9. 服务变化时的排查顺序

当一个命令突然失败，按下面顺序定位，避免先改公共 transport：

1. 运行该服务的 `status` 或只读命令，确认是网络不可达、入口改址、认证失效还是业务响应变化。
2. 查看 JSON 中的 `code`、`evidence`、`request` 和 `response`；先判断失败是否发生在 adapter 之前。
3. 如果返回登录页，检查会话文件和认证流程；不要把登录页当作业务空结果。
4. 如果只是字段解析失败，重新观察真实响应，优先在该服务 adapter 中修复映射。
5. 如果写请求返回未确认，先用只读命令回读状态；确认没有重复写入风险后再决定是否重试。
6. 如果服务返回 403、5xx、默认页或连接错误，保留具体证据并降低能力承诺；只有重新发现协议后才恢复高置信度能力。

## 10. 当前边界和已知限制

- 需要浏览器执行 JavaScript、强制浏览器指纹或不可导出的设备认证时，不能仅凭现有 CLI 协议保证等价支持。
- 需要图形验证码的流程不会自动完成；调用方必须提供验证码值。
- 校内网、VPN、服务账号和权限是外部前置条件；本地测试不会证明当前账号在线上有权限。
- 没有稳定接口的旧 HTML 页面会受到页面结构变化影响，但解析代码应被限制在对应 adapter 内。
- 服务目录与页面状态是探测时的证据，不是学校服务的长期 SLA，也不是接口版本承诺。

维护的基本原则是：公共命令语义尽量稳定，协议细节集中在 adapter，结果证据明确可追溯；遇到不确定性时减少承诺，不制造不存在的业务能力。
